# What Is a System?

## Learning Objective

By the end of this lesson, you should be able to:

* Explain **what a system is** in simple words.
* Identify the **main components** of a system.
* Understand how components **interact** with each other.
* Identify a system's **inputs and outputs**.
* Explain what **state** means and why systems need to remember things.
* Identify a system's **dependencies**.
* Understand the idea of a **system boundary** — what is inside the system and what is outside.
* Look at a simple application and start thinking about it as a **system**, not just a piece of code.

> **The goal is not to memorize definitions. The goal is to learn how to look at a system and see its parts, relationships, and responsibilities.**

## In One Sentence

**A system is made of components, interactions, inputs, outputs, state, dependencies, and boundaries.**

A useful mental model is:

```mermaid
flowchart TD
  accTitle: A system
  accDescr: Input enters the system and output leaves it. Inside, components lead to interactions, which lead to state; the system also has dependencies. The system connects to the external world.
  IN["Input"] --> SYS
  subgraph SYS["SYSTEM"]
    direction TB
    C["Components"] --> I["Interactions"] --> S["State"]
    S ~~~ D["Dependencies"]
  end
  SYS --> OUT["Output"]
  SYS --> EW["External World"]
```

# 1. System vs Application

These words are often used interchangeably, but they are not the same thing.

An **application** is usually a piece of software built to perform a particular function.

A **system** is broader.

For example, an online shopping application may contain:

```mermaid
flowchart TD
  accTitle: A web application as a system
  accDescr: The user uses a browser or mobile app, which calls the web server, which calls the application. The application uses a database, a cache, a payment provider, and an email or notification service.
  U["User"] --> B["Browser / Mobile App"] --> W["Web Server"] --> A["Application"]
  A --> DB["Database"]
  A --> C["Cache"]
  A --> P["Payment Provider"]
  A --> E["Email / Notification Service"]
  %% Invisible links stack the four services in two rows, so the diagram fits a phone.
  DB ~~~ P
  C ~~~ E
```

The application is only one part of the overall system.

The complete system includes:

* users
* client applications
* servers
* databases
* networks
* external services
* data
* processes
* rules
* operational procedures

### Important

When designing systems, don't ask only:

> “How do I build this application?”

Ask:

> **“What are all the parts involved in producing this outcome?”**

That shift in thinking is the beginning of system design.

---

# 2. Components

A **component** is a distinct part of a system that performs some responsibility.

For a simple web application:

```mermaid
flowchart TD
  accTitle: Parts of a web application
  accDescr: A web application has three parts: frontend, backend and database.
  W["Web Application"] --> F["Frontend"]
  W --> B["Backend"]
  W --> D["Database"]
```

For a larger system:

```mermaid
flowchart LR
  accTitle: A system broken into layers
  accDescr: A system has clients, a backend and a data layer. Clients are web, mobile and API. The backend has auth, orders and users. The data layer has SQL, cache and files.
  S["System"] --> CL["Clients"]
  S --> BE["Backend"]
  S --> DL["Data Layer"]
  CL --> WEB["Web"]
  CL --> MOB["Mobile"]
  CL --> API["API"]
  BE --> AUTH["Auth"]
  BE --> ORD["Orders"]
  BE --> USR["Users"]
  DL --> SQL["SQL"]
  DL --> CACHE["Cache"]
  DL --> FILES["Files"]
```

A component does not necessarily mean a separate server or application.

A function can be a component.

A database can be a component.

A service can be a component.

A complete system can itself become a component of a larger system.

### Key idea

> **The boundary of a component depends on what you are trying to understand.**

---

# 3. Interactions

Components become a system because they **interact**.

Consider a login:

```mermaid
sequenceDiagram
  accTitle: A login request
  accDescr: The browser sends POST /login to the application. The application queries the user in the database and receives the user record, then returns the authentication result to the browser.
  participant B as Browser
  participant A as Application
  participant D as Database
  B->>A: POST /login
  A->>D: Query user
  D-->>A: User record
  A-->>B: Authentication result
```

The database by itself does not authenticate the user.

The application by itself does not contain the user's stored record.

The result comes from their interaction.

Interactions can happen through:

* function calls
* HTTP requests
* database queries
* messages
* events
* files
* network connections
* shared memory

System design is largely about understanding these interactions.

# 4. Inputs and Outputs

Every useful system receives something and produces something.

```mermaid
flowchart LR
  accTitle: Input, system, output
  accDescr: Input goes into the system, which produces output.
  I["Input"] --> S["System"] --> O["Output"]
```

For an e-commerce system:

```mermaid
flowchart TD
  accTitle: Placing an order
  accDescr: The input is a customer placing an order. The system produces four outputs: order created, payment processed, inventory updated, and confirmation sent.
  IN["Input:<br/>Customer places an order"] --> S["System"]
  S --> OUT["Output:<br/>Order created<br/>Payment processed<br/>Inventory updated<br/>Confirmation sent"]
```

Inputs may include:

* user actions
* HTTP requests
* uploaded files
* messages
* sensor data
* scheduled jobs
* events from another system

Outputs may include:

* HTTP responses
* database changes
* messages
* notifications
* generated files
* external API requests

### Why this matters

If you clearly identify the inputs and outputs, you can begin asking:

* How much input will arrive?
* How quickly must the system respond?
* What happens if input increases?
* What happens if an output fails?
* Which component is responsible for producing the output?

These questions eventually lead to architecture decisions.

# 5. State

**State is information about what a system currently remembers.**

For example:

```text
User: Ranjit
Logged in: Yes
Cart items: 3
Order status: Paid
Account balance: ₹2,500
```

That information represents state.

A system can have state in many places:

```mermaid
flowchart LR
  accTitle: Where state lives
  accDescr: The browser holds cookies, local storage and cached data. The application holds in-memory state. The database holds persistent state. The cache holds temporary state.
  B["Browser"] --- B1["Cookies"]
  B --- B2["Local Storage"]
  B --- B3["Cached data"]
  A["Application"] --- A1["In-memory state"]
  D["Database"] --- D1["Persistent state"]
  C["Cache"] --- C1["Temporary state"]
```

State is important because it affects how systems scale.

Suppose one application server stores a user's session in its memory:

```mermaid
flowchart TD
  accTitle: Request to server A
  accDescr: The user's request reaches server A, which holds the session.
  U["User"] --> S["Server A"] --- SE["Session"]
```

Now the next request reaches Server B:

```mermaid
flowchart TD
  accTitle: Request to server B
  accDescr: The user's next request reaches server B, which has no session.
  U["User"] --> S["Server B"] --- SE["No session"]
```

The system now has a problem.

This is one reason **stateless application design** becomes important when systems scale.

We will study that later.

# 6. Dependencies

A component rarely works completely by itself.

A **dependency** is something a component relies on to perform its job.

Example:

```mermaid
flowchart TD
  accTitle: Order service dependencies
  accDescr: The order service depends on the database, the payment service and the notification service.
  O["Order Service"] --> D["Database"]
  O --> P["Payment Service"]
  O --> N["Notification Service"]
```

The Order Service depends on all three.

If the payment service becomes unavailable:

```mermaid
flowchart TD
  accTitle: A failed dependency
  accDescr: The order service calls the payment service, which is down, so the call fails.
  O["Order Service"] -. X .-> P["Payment Service<br/>DOWN"]
```

the order flow may be affected.

This leads to an important system-design question:

> **What happens when a dependency fails?**

Possible strategies include:

* timeout
* retry
* fallback
* queue the work
* return an error
* degrade functionality

Later chapters will build these ideas systematically.

# 7. Boundaries

A **boundary** defines what belongs to a system or component and what does not.

Consider an online store:

```mermaid
flowchart TD
  accTitle: A system boundary
  accDescr: Our system contains the frontend, backend and database. It calls the payment provider, an external system, through an API.
  subgraph OUR["OUR SYSTEM"]
    direction TB
    F["Frontend"] --- BE["Backend"] --- DB["Database"]
  end
  subgraph EXT["External System"]
    P["Payment Provider"]
  end
  OUR -->|API| P
```

The payment provider is a dependency, but it is outside our system boundary.

Boundaries help answer:

* Who owns this component?
* Who controls this data?
* Who is responsible when it fails?
* How do components communicate?
* Where does one system end and another begin?

Poorly defined boundaries often create tightly coupled systems.

---

# 8. A System Is More Than Its Parts

Imagine:

```text
Database
+
Application
+
Network
```

Simply putting these components together does not automatically create a good system.

Their **relationships** matter.

For example:

```mermaid
flowchart LR
  accTitle: Application dependencies
  accDescr: The application depends on the database and on an external API.
  A["Application"] --> D["Database"]
  A --> E["External API"]
```

Now consider:

* How often does the application call the database?
* How much data does it transfer?
* What happens when the database is slow?
* What happens when the external API fails?
* Can the application continue without it?
* Where is state stored?

The architecture emerges from these relationships.

> **System design is not just choosing components. It is designing how components interact.**

# 9. A Small Real-World Example

Consider a food-ordering system.

A customer places an order.

```mermaid
flowchart TD
  accTitle: A food-ordering request
  accDescr: The customer uses the mobile app, which calls the API. The API uses the order database, the payment system and the restaurant system. The restaurant system leads to the order being ready.
  C["Customer"] --> M["Mobile App"] --> A["API"]
  A --> OD["Order<br/>Database"]
  A --> P["Payment<br/>System"]
  A --> R["Restaurant<br/>System"]
  R --> OR["Order Ready"]
```

The system receives:

```text
Input:
"Customer wants one pizza."
```

It must maintain state:

```text
Order #1042
Status: Preparing
Payment: Paid
```

It depends on:

```text
Database
Payment provider
Restaurant system
```

It produces outputs:

```text
Order confirmation
Payment result
Restaurant notification
Customer notification
```

And it has boundaries:

```mermaid
flowchart LR
  accTitle: Our platform and what it connects to
  accDescr: Our platform contains an API, a database and order logic. The order logic connects to the payment provider and the restaurant system.
  P["Our Platform"] --- API["API"]
  P --- DB["Database"]
  P --- OL["Order Logic"]
  OL --- PP["Payment Provider"]
  OL --- RS["Restaurant System"]
```

Now we can start asking architectural questions.

What happens if 10 customers order simultaneously?

What happens if 10,000 customers order simultaneously?

What happens if the payment service becomes slow?

What happens if the database fails?

What happens if the restaurant system is unavailable?

These are **system-design questions**.

# 10. The System Model

For Systemly, use this mental model whenever you encounter a new system:

```mermaid
flowchart TD
  accTitle: The parts of a system
  accDescr: Inputs enter the system and outputs leave it. Inside, components lead to interactions, then state, then dependencies. The system's boundary separates it from the external world.
  IN["Inputs"] --> SYS
  subgraph SYS["SYSTEM"]
    direction TB
    C["Components"] --> I["Interactions"] --> S["State"] --> D["Dependencies"]
  end
  SYS --> OUT["Outputs"]
  SYS ---|Boundary| EW["External World"]
```

When looking at any architecture, identify these seven things:

| Element          | Ask                                    |
| ---------------- | -------------------------------------- |
| **Components**   | What are the parts?                    |
| **Interactions** | How do the parts communicate?          |
| **Inputs**       | What enters the system?                |
| **Outputs**      | What leaves the system?                |
| **State**        | What does the system need to remember? |
| **Dependencies** | What does it rely on?                  |
| **Boundary**     | What is inside and outside?            |

This simple checklist will remain useful even when systems become extremely complex.

---

# 11. Why This Matters for System Design

A beginner often sees an architecture like this:

```mermaid
flowchart TD
  accTitle: A chain of technologies
  accDescr: Client, then load balancer, then API, then Redis, then database, then Kafka.
  C["Client"] --> LB["Load Balancer"] --> API["API"] --> R["Redis"] --> D["Database"] --> K["Kafka"]
```

and thinks:

> “I need to learn what all these technologies are.”

That is the wrong starting point.

Instead ask:

```mermaid
flowchart TD
  accTitle: Questions for analysing a system
  accDescr: Ask in order: what is the system trying to do, what are its components, how do they interact, what state exists, what dependencies exist, what constraints exist, and what problem requires another component.
  Q1["What is the system trying to do?"] --> Q2["What are its components?"] --> Q3["How do they interact?"] --> Q4["What state exists?"]
  Q4 --> Q5["What dependencies exist?"] --> Q6["What constraints exist?"] --> Q7["What problem requires another component?"]
```

Only then should you decide whether something like Redis, Kafka, or a load balancer is necessary.

> **Architecture should emerge from the problem, not from a list of technologies.**

---

# 12. The First System-Design Habit

Whenever someone presents you with a system, resist the temptation to immediately draw a complex architecture.

Start with:

```text
1. What does the system do?

2. What goes into it?

3. What comes out?

4. What are its components?

5. How do those components interact?

6. What state must be remembered?

7. What does it depend on?

8. Where is the system boundary?
```

Then ask:

```text
What can become a bottleneck?

What can fail?

What happens when usage grows?

What must remain available?

What can be delayed?

What must happen immediately?
```

Those questions gradually turn a simple application into a system you can reason about.
